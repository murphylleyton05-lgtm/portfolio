1 · Arquitectura del sistema

El sistema separa el razonamiento estratégico (Manager) de la ejecución especializada (Workers). El Manager recibe la petición, clasifica la intención dentro de una taxonomía cerrada de negocio y delega a un especialista quirúrgico mediante Execute Workflow, pausándose hasta recibir el resultado estructurado. Cada acción queda registrada en un log de trazabilidad.

Regla de oro: el Manager decide y coordina; los Workers ejecutan una única tarea atómica. Ningún especialista vive dentro del lienzo principal — se rompe por completo el antipatrón "mono-bloque".

3 · Esquema de datos (Contrato de Interfaz)

El contrato es el "idioma común" entre Manager y Workers. Se transfiere el mínimo producto viable (evita el Pasillo de la Muerte por data stuffing) y cada Worker devuelve una envoltura estándar con status, de modo que el Manager siempre sabe interpretar la respuesta, incluso ante fallos.

Ida · Manager → Worker 1

// solo lo imprescindible
{
  "requestId": "REQ-1699...",
  "intencion": "BUSQUEDA_EMPLEOS",
  "terminos": ["automation","data analyst"],
  "limite": 12
}

Ida · Manager → Worker 2

{
  "requestId": "REQ-1699...",
  "intencion": "REDACCION_EMAIL",
  "destinatario": "tu@mail.com",
  "tono": "profesional",
  "vacantes": [{ "titulo":"...", "url":"..." }]
}

Vuelta · Worker → Manager (éxito)

{
  "status": "success",
  "worker": "worker1_extraccion_datos",
  "requestId": "REQ-1699...",
  "data": { "count":12, "vacantes":[...] },
  "error": null
}

Vuelta · contingencia ante fallo

{
  "status": "error",
  "worker": "worker1_extraccion_datos",
  "requestId": "REQ-1699...",
  "data": null,
  "error": { "code":"API_UNREACHABLE",
             "message":"..." }
}

4 · Criterio de enrutamiento

El Manager clasifica el lenguaje natural del usuario en una taxonomía cerrada de tres categorías de negocio. El Router de Triaje (IA) propone la categoría; un Parser la normaliza y, si la IA no está disponible o responde fuera de formato, aplica un fallback determinista por palabras clave (costo 0 tokens). Un nodo Switch enruta de forma determinista sobre el campo intencion, y la ruta de fallback actúa como vía de escape hacia un supervisor humano.

Categoría (taxonomía cerrada)Se delega aDisparadores
BUSQUEDA_EMPLEOSWorker 1 · extracción y análisisbuscar / listar vacantes, puestos, oportunidades
REDACCION_EMAILWorker 2 · redacción de correosredactar / escribir correo, postulación, carta
ESCALAR_HUMANO (fallback)Supervisor humanointención dudosa, ambigua o fuera de taxonomía

5 · Antipatrones evitados

  • Mono-bloque / flujo espagueti: cada especialista vive en su propio lienzo, iniciado por Execute Workflow Trigger.
  • Pasillo de la Muerte (data stuffing): un nodo Set de limpieza transfiere sólo el mínimo producto viable (IDs, términos), nunca binarios ni metadatos pesados.
  • Time-outs sin control: HTTP Request con timeout: 15000 y sub-workflows con executionTimeout; el Manager pausa con Wait for child to finish.
  • Fallos silenciosos del Worker: cada Worker termina devolviendo un JSON de contingencia (status:"error") — el Manager nunca se bloquea.

6 · Testing de regresión (validación previa)

Antes de armar este PDF se ejecutó el Manager manualmente y se verificó en el panel de ejecución que: (1) el Manager delega al Worker correcto según la intención, (2) el Worker responde con su contrato JSON, y (3) el resultado vuelve integrado al contexto del Manager y se registra en el log. Se probaron las tres rutas cambiando el texto en el nodo Consulta del usuario.
